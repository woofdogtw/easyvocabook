# 日文動詞自他對應測驗 探索

## 動機

日文動詞測驗希望加考「對應的自動詞／他動詞」。若該動詞沒有對應詞，使用者必須**留空**，
亂填要算錯——這一項也納入正確與否的判定。只在日文顯示。

## 現況：資料在，但測驗用不到

`transitive_pair` 這個 label 兩平台的 canonical list 早就有，連翻譯（對應及物動詞）都在，
但 `suggested_labels("ja","verb")` 不含它，且資料庫裡一筆 `transitive_pair` 都沒有。

真正的資料躺在 `words.note` 的自由文字裡：

```
起きます  →  note = "動詞類: 2、自動 / 自他: 起こす"
働きます  →  note = "動詞類: 自動"            ← md 原本是 -，代表無對應詞
```

`~/tmp/gen_vocab_sql.py` 把 md 的「動詞類」與「自他動詞對照」兩欄合併塞進 `note`，
測驗引擎不會碰 `note`，所以這項功能等於完全沒接上。

**注意**：產生腳本把 md 的 `-`（確定無對應）和空白（未確認）壓成同一種輸出，
所以光看現有 DB 分不出兩者；那個區別只存在於 md 原檔。

## 來源資料盤點（`~/tmp/單字-動詞.md`，284 個動詞）

| 自他動詞對照 | 筆數 |
|---|---|
| 有對應詞 | 105 |
| `-`（確定無） | 179 |
| 空白 | 0（105 + 179 恰為 284） |

動詞類（自動／他動）欄則很稀疏，且與「有無對應詞」幾乎不相關：

```
            有對應詞   無對應詞
有標自他      40        66
未標          65       113     ← 65 個有對應詞卻沒標類型

178 / 284（63%）不知道是自動詞還是他動詞
```

## 決策

| # | 議題 | 決策 |
|---|------|------|
| ① | 資料如何進入測驗 | **重新從 `~/tmp` 的 md 產生 SQL**，寫進結構化的 `word_forms.transitive_pair`，不再依賴 `note` 自由文字 |
| ② | 「無對應詞」如何表達 | **不存那一列**；答案面顯示 `-` |
| ③ | 空欄位的批改規則 | **全面套用**「目標字自己的空欄位 → 必須留空」，不限 transitive_pair |
| ④ | 自動詞／他動詞類型 | **加入並計分**（需補齊 178 個動詞的類型資料） |
| ⑤ | 既有使用者資料 | **全部捨棄**，schema 直接**重置回 v1**，不做遷移 |
| ⑥ | 類型的 UI 與分類數 | **三顆 radio button**：自動詞／他動詞／自他両用 |
| ⑦ | seed 產生方式 | 從 `~/tmp` 的 md **重頭建立**，產生腳本亦可重寫 |

### ② 的理由

`transitive_pair` 對日文動詞是必定顯示的欄位，使用者一定會看到它，
所以「留空」本身就是一種主張（我查過了，沒有對應詞），而非「還沒填」。
這樣不需要改 schema，也不必推翻 `word-form-reading` 訂下的「value 與 reading 皆空的列會被丟棄」規則。

### ③ 的範圍與例外

```
目標字自己的空欄位  →  必須留空（新規則，嚴格）
同義字缺該欄位      →  接受任何輸入（維持寬鬆）
```

同義字那條寬鬆例外必須保留：拿別的字批改時，該字缺變化資料不該扣使用者分。

全面套用會一併解決 `word-form-reading` 留下的尾巴——名詞的量詞／助詞、形容詞的變化欄位
在使用者資料裡都是空的，目前「隨便填都對」，共影響 873 / 1157 字。
兩者是同一個病根，分兩次修要動同一段程式碼兩次。

### ④ 的資料缺口與補法

不需人工逐一查字典：

1. **從對應關係推導**——有對應詞的 105 組，兩者必為相反類型
2. **構詞規律**——自他動詞對有很強的規律（起きる／起こす、始まる／始める、開く／開ける）
3. **助詞提示**——md 有 `自動(が)` / `他動(を)` 可交叉驗證
4. 其餘為 N5／N4 常用動詞，可由 agent 產生草稿供人工複核

重新產生 seed 時一併補上，使用者只需複核。

### 兩個獨立的軸（原本被混為一談）

```
軸一：這個動詞本身是什麼？     自動詞 ／ 他動詞      ← 必有其一
軸二：有沒有對應的另一邊？     有 → 填對應詞
                               沒有 → 留空（顯示 -）
```

原先設想的第三個選項「什麼都不是」其實屬於**軸二**，已由 `transitive_pair` 留空表達，
所以軸一只需要兩個選項。

語言學上唯一的第三類是**自他両用動詞**（ドアが開く／ドアを開く 皆成立）。
查證來源資料：沒有任何動詞同時標記自他，連 `閉じる` 都被當作他動詞配 `閉まる`。
故兩分類對本專案的詞彙量足夠，不需要為両用另設一類。

### ⑤ 重置回 v1，而非升到 v3

目前只有作者一人使用，練習統計（practice_count / correct_count）可以接受歸零。
既然資料整個重建，schema 就**直接改寫 v1 的 CREATE 語句**（一次含 `word_forms.reading`
與新的動詞類型欄位），並**刪除 v1→v2 遷移**。版本號留給真正上架之後再用。

清除計畫：PC 直接砍檔、Android 清除 App 資料、雲端手動清除，之後 PC 開啟後同步上雲。
因此「舊 v2 檔被新 app 拒開」的風險不存在。

**已知代價（明確接受）**：v1→v2 是遷移機制目前唯一被實際執行與測試的地方，
其中包含守住 A1 缺陷的 `v1DatabaseFromDesktop_withZeroUserVersion_stillMigrates`
（桌面版產生的檔 `user_version = 0`，Android 會誤走 no-op 的 `onCreate` 而漏掉遷移）。
全部刪除後，`migrateFromDbInfo` 會成為沒有步驟可跑的空殼，
要到上架後第一次改 schema 才會再被執行。曾提議保留一個「只驗證驅動邏輯」的測試，
作者決定不保留。

### ⑥ 為什麼是三顆而不是兩顆

「什麼都不是」屬於軸二，已由 `transitive_pair` 留空表達，所以軸一不需要它。
但語言學上真正的第三類是**自他両用動詞**：

- `閉じる`（目が閉じる／目を閉じる）——來源 md 當作他動詞配 `閉まる`
- `終わる`（会議が終わる／会議を終わる）——來源 md 標為自動
- 其他：`開く`（花が開く／本を開く）、`増す`、`吹く`（風が吹く／笛を吹く）

兩顆會逼使用者對這類動詞選一個錯的答案。三顆的成本為零——現有 284 個動詞照 md 分成兩類即可，
第三類留給日後新增或修正的字；且三選一必定恰好一個答案，不像兩個 checkbox 會出現
「都沒勾」的無效狀態。

## 衍生工作（不屬於本 change）

### seed 產生要做成 skill

補完動詞類型、自他判斷、例句這些都不是固定程式碼能解決的——需要語言模型判斷。
而作者會持續維護 md，所以需要一個「教模型如何把 md 轉成乾淨 SQL」的 skill。

決策：

- **模型每次重新判斷，不寫回 md（方案 A）**。md 是作者個人的整理習慣，
  skill 應盡量適應不同人的風格，而不是反過來要求 md 符合某種被擴充的格式。
  優化留給未來更強的模型。
- **不可重現性不是問題**：一旦 app 支援「匯入 SQL 新增單字」，工作流會變成
  「md 新增幾行 → 只為那幾行產生 SQL → 匯入」，舊字不動、統計保留。
  每個字只會被判斷一次，判完就存進 DB。**DB 才是累積器，不是 md。**
- **放在 `~/ai/ai-skills/skills/`**，與既有的 `sylvia-iot-services` 並列，
  代表作者個人的 skill 集，可從單一 README 瀏覽。
  （代價：skill 需要知道 schema，schema 改動時要記得同步更新，
  這點放在專案內會比較不容易漏掉，但作者選擇可瀏覽性。）
- **獨立於本 change**：本 change 需要資料才能驗證，因此 seed 以一次性的方式產生；
  通用化的 skill 留到本 change 完成後再做。

### 助詞／介系詞應歸為「搭配」而非名詞屬性

探索過程中確認：助詞（日）與介系詞（英）是**關係性**的，取決於單字在句中的角色，
不是名詞本身的性質——這也是本 change 把 `(ja, noun) → counter, particle` 整條移除的原因。

但換成動詞／形容詞的角度就成立了，那是單字本身的用法：

```
日文：会う → 〜に会う（不是 を）      英文：interested → interested in
      乗る → 〜に乗る                        depend     → depend on
```

英文的 canonical label 早就有 `collocation`，那正是這個概念的正確名稱。
日後若要考這一項，方向是「動詞／形容詞的搭配」，而非「名詞的助詞」。

因此 `verb-transitivity` 一併刪掉 quiz-engine 裡「JA 字若有 `particle` 資料就加該欄位」
這條規則——兩平台從未實作、全庫也沒有任何一列用到該 label。空頭規則留著只會與
「日文名詞只考單字」互相矛盾。`particle` 仍留在 canonical list 中可手動選用。

### 之後還想要的 app 功能

「匯入 SQL 新增單字」——讓使用者自行擴充字庫，也是上述增量工作流的前提。

## 未決問題的處理（已定案）

### ① 判不出類型的動詞 → 全部由模型判定，作者複核

md 的標記極不對稱：標「自動」104 個、標「他動」**只有 2 個**、未標 178 個。
作者只在「是自動詞」時註記，所以「未標」語意是空的——既非未知也非他動。

推導覆蓋率分層：

| 來源 | 數量 | 可靠度 |
|---|---|---|
| 已明確標記 | 98 | 高 |
| 由對應詞反推（對應詞在清單且已標，A↔B 必相反） | 18 | 高 |
| 有對應詞，靠構詞規律推 | 41 | 中 |
| **無對應詞，需語言知識判定** | **104** | 模型判斷 + 人工複核 |

這 104 個正是「機車計分」的風險所在（判錯會讓使用者答對卻被算錯），
也正是把 seed 產生做成 skill 的核心價值——固定程式碼做不到這件事。

### ② `note` 的結構化 → 盡量結構化，且組別用機械推導

`note` 目前塞了兩種資訊，且對非動詞另有用途（名詞放 md 的「補充」欄），不能整欄清除。

拆解後發現 `動詞類` 其實混了兩個維度：

- **動詞組別**（I/II/III 類）：`2`（9 個）、`3`、`*`（する・ある・いる・来る）、
  空白（176 個，實為 I 類預設）
- **自他類型**：`自動` / `他動`

**組別可以純機械推導，不需模型判斷**，而且比 md 自己的標記更完整
（284 列共 261 個不重複原形，覆蓋率表以原形為單位）：

```
原形 + ない形 → 組別        （ない形 284 個全部都有，零缺漏）

起きる → 起きない   去る不變音  → II 類
働く   → 働かない   く→か 變音  → I 類
終わる → 終わらない る→ら 變音  → I 類  ← 結尾是る但不是一段
勉強する → 勉強しない           → III 類
```

確切數量取決於規則細節（複合動詞 `持って　来る` 屬不規則、`冷やしない` 是來源錯字），因此以「全數可分類 + 回報異常」為準，不寫死數字。
例如 `寝る` 作者只標「自動」未標組別，但 ない形 直接證明它是 II 類。

因此兩個欄位的取得方式明確分工：

| 欄位 | 來源 | 可靠度 |
|---|---|---|
| 動詞組別 | 原形 + ない形 機械推導 | 100%，可驗證 |
| 自他類型 | 模型判斷 104 個 + 人工複核 | 需把關 |

### ③ 一致性驗證 → 只在產生 seed 時檢查

不變式：若 A 的對應詞是 B，則 A 與 B 必為相反類型。

資料實況（以原形比對）：

```
對應詞也在清單且互指   40   ← 可雙向交叉驗證
對應詞在清單但未互指    4   ← 資料不一致，應修正
對應詞不在清單         52   ← 無法驗證（對應詞不是獨立單字）
```

52 筆的對應詞根本不是清單中的單字，app 層驗證意義不大；
但產生 seed 時做一次全域檢查很划算——能抓出那 4 筆不一致，以及模型判錯的地方。
驗證產出報告供人複核，不阻擋產生流程。
